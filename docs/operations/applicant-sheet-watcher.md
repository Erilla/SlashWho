# Applicant Sheet watcher

Intake starts evidence for the submitted character. Its discovery also queues
full evidence for each Raider.IO linked character before fingerprint admission
or snapshot publication, without requiring a dossier read. These linked runs
record origin `discovery` and the submitted character as their root. Fresh
evidence is reused and active collections coalesce; newly admitted fingerprint
matches keep their existing `fingerprint_admission` policy. The evidence queue
remains serial and applies its normal points gate and retry policy.

The worker reads Battletag, Discord ID, and Character Name from columns B:D, plus the configured character-link column of the `Form Responses` tab, starting at row 2. It also reads column A (the Forms timestamp) as a raw spreadsheet serial, in a second request together with the link column. The second read compares the parsed character links in each row with the first. If they differ in anything except rows appended at the end (for example after a sort or a deletion), the poll fails without advancing, and retries on the next tick. The largest serial seen is kept as `submitted_serial_mark`, and only responses above it can become applications. It uses separate Sheets values ranges so unrelated form answers between D and the link column are not read. It starts discovery plus evidence for new supported character links and never writes to the Sheet. When a new response lists more than one character, the worker also records it as an application. With `APPLICANT_LINKING_ENABLED=true`, it links every other character to the first one as a manual connection labelled "From application", once each character exists and passes the checks: not suppressed, the same region, not excluded on either dossier (under any name sharing its Warcraft Logs id), and not already in a different multi-character group. A response with more than 5 character links is never linked. Settlement of recorded applications runs on every tick, whatever the flag says, and still runs when the drain fails; only the linking step depends on the flag. Seven days after settlement an application's undecided members are `expired` and it closes, before any link is considered, so switching linking on after a pause never links a backlog in one burst. The hourly maintenance cleanup applies the same 7-day expiry, closes applications still open 30 days after they were recorded, and deletes closed ones 30 days on. It runs whatever `APPLICANT_WATCHER_ENABLED` and `APPLICANT_LINKING_ENABLED` say. The `applicant_links` event counts each outcome: `linked`, `waiting`, `suppressed`, `same_character`, `skipped_region`, `skipped_excluded`, `skipped_cross_group`, `needed_link_pairs`, `expired` and `failed`. Read `skipped_cross_group` against `needed_link_pairs`. An application whose processing throws is rolled back, moved to the back of the queue and counted in `failed`, without logging any message. The step's other events are `applicant_applications_settle_failed`, `applicant_links_failed`, `applicant_applications_cleanup` and `applicant_applications_cleanup_failed`. The first successful read after activation establishes a baseline; existing responses produce no intents. Occurrence counts, not row positions, track later changes. Reorders are inert; an increased count creates a new intent, including after a deletion observed by a prior poll. A deletion and replacement by another response with the same character count entirely between polls cannot be distinguished from no change. This snapshot limit also applies to deleting and re-adding the same response between polls.

The watcher is disabled by default. Configure either `APPLICANT_SHEET_URL` (a `https://docs.google.com/spreadsheets/d/...` URL) or `APPLICANT_SHEET_ID`. Do not set both URL and ID. For a Sheet intentionally shared with anyone who has the link, set `APPLICANT_GOOGLE_API_KEY` to a key restricted to the Google Sheets API. The worker sends it in an `x-goog-api-key` header, not in the request URL. For a private Sheet, arrange **viewer** access to the specific file for a dedicated Google service account and set `APPLICANT_GOOGLE_SERVICE_ACCOUNT_EMAIL` plus `APPLICANT_GOOGLE_PRIVATE_KEY`. Do not combine API-key and service-account credentials. The credential owner must retain the ability to rotate or revoke credentials and remove sharing. The private key uses `\n` for line breaks. Set `APPLICANT_SHEET_COLUMN` to the column containing character links if it is not `F`; the worker validates the column name. Check the chosen column before enabling, since adjacent applicant answers may be private. Set `APPLICANT_DOSSIER_BASE_URL` to the HTTPS origin of the matching web environment (for example, `https://web-test-7765.up.railway.app`) so the alert links to its dossier. The service-account OAuth scope is `spreadsheets.readonly`; the configured ranges are narrow data reads, not a permission boundary for the Sheet.

Set `APPLICANT_POLL_CADENCE_MS`, `APPLICANT_ADMISSIONS_PER_TICK`, `APPLICANT_ADMISSIONS_PER_DAY`, `APPLICANT_BACKLOG_LIMIT`, `APPLICANT_QUEUE_DEPTH_LIMIT`, `APPLICANT_MINIMUM_POINTS`, and `MAINTAINER_ALERT_WEBHOOK_URL` explicitly before setting `APPLICANT_WATCHER_ENABLED=true`. The watcher runs on its own pg-boss schedule, `applicant-sheet-tick`, every minute (UTC). At most one tick is queued or running across all workers. `APPLICANT_POLL_CADENCE_MS` (60000 to 3600000) sets how often a tick reads the Sheet. A poll is due 15 s early, measured from the previous poll's start, so a one-minute cadence polls about every minute. pg-boss cron ticks can start up to about 30 s late, so an occasional gap of about 2 minutes between polls is expected. Admissions drain on every tick. After the Warcraft Logs allowance blocks a drain, the drain and its points probe pause for 5 minutes. The poll's own Warcraft Logs id check shares that same 5-minute block: a block set by either one pauses both the drain and numeric-id resolution. Measure recent `character_evidence_run_costs` for own credentials and the Warcraft Logs allowance before choosing limits. The worker requires remaining points of at least the greater of `APPLICANT_MINIMUM_POINTS` and 120% of the largest measured own-credential cost in the last 28 days, after reserving that amount for each queued or active own-credential evidence run. The daily cap charges each new canonical dispatch once; retries and duplicate links in the same poll do not spend another admission slot. The existing evidence worker remains serial and applies its own points gate.

A Discord channel webhook can be used as `MAINTAINER_ALERT_WEBHOOK_URL`; the worker escapes applicant text and suppresses mentions. Other HTTP alert receivers receive structured `{ event, details, applicant }` JSON for arrivals.

The worker sends `applicant_new_intents` to `MAINTAINER_ALERT_WEBHOOK_URL` once per new response, in the poll that first sees it, even when all of its links were deferred; a deferred link admitted later does not alert again. Each alert contains Battletag, Discord ID, Character Name, the first character's supported URL and matching site dossier URL, and how many other characters the response listed. A response with more than one character also has a `Linking:` line: they will be linked if they pass the checks, there are too many to link automatically, or automatic linking is off. A numeric Warcraft Logs character ID has a dossier URL when it resolves during that poll; otherwise the alert marks dossier resolution pending. Baseline and unchanged polls send no arrival alert. Delivery is best effort and a failed webhook never rolls back the intake. Discovery and evidence run messages still use `DISCOVERY_WEBHOOK_URL`.

Every observed count increase has its own outbox intent. Two responses for the same character first seen in one poll share the discovery/evidence run, because no collection can become stale between their first observation. A submission first seen in a later poll gets a new freshness decision.

When the same character appears in multiple rows, the alert uses the later occurrence for a count increase. This matches append-only form responses; a reorder or insertion of a duplicate between polls can make the applicant details ambiguous even though intake counts remain correct.

Set `APPLICANT_WATCHER_ENABLED=false` to pause reads and dispatch. The outbox remains durable. Watch count-only `applicant_sheet_poll`, `applicant_sheet_poll_failed`, `applicant_sheet_drain`, `applicant_sheet_drain_failed` and `applicant_sheet_tick_failed` events. `applicant_poll_failed` is sent once polls have been failing continuously for 15 minutes (at most hourly), with `failures` and `failingMinutes`. It is checked on every tick, including ticks the failure back-off skips, so it does not wait for the next retry. A repeated failure, a backlog near its configured limit, or a spent allowance requires operator attention. The first activation intentionally drops all previously visible responses as baseline. Do not reset the `applicant_source_*` tables unless a new baseline is intended. Revoking access causes failed polls without changing the durable cursor.

A change to what the link parser accepts is handled by `applicantParserVersion` in `apps/worker/src/applicant-candidates.ts`. Bump it whenever the parser starts or stops reading a kind of link; a unit test pins the parser's outcomes on a fixed corpus to each version and fails until you do. The first poll under a new version re-baselines: it records the new counts without creating intents, so responses the new parser reads for the first time are not announced, and the poll logs `rebaselined: true`. Submissions deferred before the change are still admitted. A genuinely new response that arrives between the last poll under the old version and the first under the new one is absorbed into the baseline and gets no alert or run, so check the Sheet for responses from around a deploy that changes the version.

Choose the Sheet URL and column before first activation. Changing either after polling has begun requires an explicit new baseline procedure for the durable source counts (run `DELETE FROM applicant_source_application_members; DELETE FROM applicant_source_applications;` before clearing the intents, and reset `submitted_serial_mark` to NULL). Never use `TRUNCATE … CASCADE` on these tables: it cascades through `manual_dossier_connections.applicant_application_id` and wipes `manual_dossier_connections`, every reviewer's manual link with it. A `DELETE` only sets that column to NULL, and the links stay. Changing the environment setting alone can treat existing responses in the new source as new submissions.

Only normalized character identities, numeric Warcraft Logs IDs, occurrence counts and positions, timestamps, outbox state, the application tables (identity strings, a Forms serial, sequences, times and counts) and the serial mark are stored. Member rows are deleted when an application closes, and closed applications are deleted after 30 days. Battletag, Discord ID, Character Name, raw Sheet cells, URLs, adjacent applicant answers, and credentials are never stored or logged by this watcher; the selected details are held in memory only until alert delivery. No production Sheet access or permission changes are part of issue #444's code delivery.

Each value in the configured column is limited to 4,096 characters. Every literal URL within that bound is inspected. An over-limit value raises a count-only `applicant_input_truncated` alert for operator correction; candidates beyond the character bound are not admitted. Increase the bound only with a matching response-size and backlog review.

Admin Settings (`/admin/settings`) does not yet hold the Sheet URL and column controls. When they move there, they need server-side validation and access restricted to admins. Until then, these are worker environment settings; changing them requires a worker restart.
