# Issue #782: resolve historic Raider.IO roster identities

## Evidence and intended outcome

A character's tier-28 first-kill list contains a Mythic final-boss kill and a logged encounter with a visible 20-player roster. The current profile ID differs from its historic roster ID, so `collectRaiderIoFirstKills` discards the kill. The dossier consequently loses both kill and roster, independently of the WCL five-page history ceiling. Public examples and regression fixtures must be anonymised.

On 2026-10-03, requesting the roster member's historic `name-<id>` profile on the historic realm returned the current profile's ID and current realm. This provides upstream identity resolution, rather than a name-based identity inference. The logged encounter's historical roster itself remains unchanged.

## Proposed design

1. Keep direct roster-ID presence as the cheapest proof. On a mismatch, resolve eligible historic roster profile entries through Raider.IO's character-detail endpoint and require the resolved profile ID to equal the subject's current ID. A name, numeric suffix, class, achievement date or kill-list association alone must never establish presence. Do not create aliases or account connections from these reads.
2. Add a narrow gateway operation for historical roster profile resolution. Validate region, realm and the upstream tombstone name: a numeric suffix must equal that roster member's recorded ID. Encode every path segment. Parse only the current resolved character ID and other minimal validation fields; never persist a raw response. Ordinary character-key validation stays unchanged. A suffix is a locator, not proof. Ordinary unsuffixed roster names must not become an identity fallback without a separate upstream proof, because a name can change owner.
3. Resolve once per unique historical roster profile in a collection run and reuse answers across its encounters. Use an explicit maximum of 50 physical identity resolutions per run and concurrency at most four. Prioritise candidates with the subject's class; obtain that class from the existing current-character read. Class filters candidates only, never proves identity. Stop launching requests on rate limiting or transient failure. Deferred/unresolved candidates preserve evidence and make the Raider.IO phase partial; they continue on an ordinary eligible full run, without scheduling a Raider.IO-only whole-evidence retry. A definitive different resolved ID remains a mismatch. Preserve the existing independent logged-encounter allowance; count these new physical requests in Raider.IO observability and request bounds. Manager review must confirm these bounds and whether a stricter candidate filter is required.
4. Set `presenceChecked` only after a direct or upstream-resolved ID match. Reuse that durable fact on later roster privacy refreshes as today. Preserve existing hidden-roster handling, unsuccessful/non-Mythic and raid/boss mismatch rejection, and partial publication guarantees. Leave the WCL scan ceiling, parse attribution and report URLs unchanged. Keep public roster membership historical; do not highlight an old-name member as a current dossier character through name heuristics.
5. Bump only `CURRENT_RAIDER_IO_TIER_READ_VERSION` from 1 to 2 so the next ordinary eligible full collection asks previously dropped historical tiers again. Keep `CURRENT_EVIDENCE_VERSION` and all WCL/parse collection versions unchanged. Accept the ordinary freshness and weekly full-collection latency described below; do not force immediate recollection. Do not issue an ad hoc production update or claim that all WCL history is complete. A normal collection should recover the Raider.IO kill and roster even when no WCL report is recovered.
6. Add sanitised regressions for direct-ID presence, historical profile resolving to the current ID, resolving to another ID, malformed suffix/unsupported keys, deduplication and request bounds, transient/rate-limit/deferred resolutions, hidden-to-visible roster rechecks, stored presence, publication/readback and public dossier roster rendering. Assertions must prove that the exact-ID mismatch remains rejected unless an upstream resolution establishes identity. Include the no-WCL-report case and tier-mark recovery.

## Durable resolution progress

Add a parsed-answer repository and additive migration for `raiderio_roster_profile_resolutions`, keyed by the validated historical locator (region, realm, tombstone name and recorded historical ID) and resolver version. Store only the positive safe integer resolved ID or classified limitation code, `answered_at`, and `last_attempt_at`; no raw response, credentials, account connection or current-character ownership edge. The shared answer is profile resolution, not subject-specific presence. Match its resolved ID to the current subject only when using it. An answer is saved before it can establish `presenceChecked` or count as durable progress. Failed persistence makes the phase partial and supplies no new proof.

Validate and deduplicate all candidates first. Reuse definitive cached answers younger than 30 days. Construct the outstanding queue deterministically: never-attempted locators first, then due attempted locators ordered by `last_attempt_at` (oldest first), with the full locator as tie-breaker. Record an attempted reservation before dispatch so failed/deferred work does not monopolise each new run. Candidates beyond the physical cap receive no attempt timestamp; consequently candidate 51 remains ahead of already attempted candidates on the next run, even if older answers have expired. Rate limiting/transient failure stops dispatch for this run; its attempted timestamp and ordinary-run continuation let other outstanding locators progress on the next eligible run. Read up to 50, reserve before each dispatch, and use at most four workers. Each response is associated with its locator; final attribution does not depend on completion order. Do not pre-reserve the entire backlog or reset the queue on partial publication.

Definitive different-ID answers remain cached and skip further physical reads until due. Stable inputs advance rather than repeating the first 50. New candidates join the same queue; no claim of bounded completion under unbounded input growth is made. Add a three-run regression with more than 100 locators and the matching subject after the first 50, plus expiration and transient-failure variants. Assert per-run physical caps, peak concurrency, stable attribution, persisted answer reuse, and the absence of repeated first-prefix admission.

## Rollout and expected correction latency

Version 2 invalidates only settled Raider.IO tier-read marks. It does not invalidate fresh completed evidence, WCL terminal tiers or parses. On deployment:

1. A fresh old completed run stays fresh until the configured evidence freshness window expires (currently 24 hours); an active reservation is still joined normally.
2. At the next stale dossier read, existing `staleReadNeedsOnlyNewestPage` rules choose full immediately for an unfinished WCL scan/parse, resume bookmark, or unsettled tiers. Otherwise an old recent successful Raider.IO kill-list read permits a light run. Light collection asks no historic tiers and therefore does not claim to correct the missing roster.
3. Light runs do not update `lastRaiderIoRecoveryAt`. Once the last successful Raider.IO recovery read is at least seven days old, the existing weekly recovery rule selects a full run on the next stale read. The full handler has a history allowance greater than one (or tier caps), asks historic tiers, ignores version-1 marks, and resolves the new identity candidates. An insufficient provider/points allowance uses existing deferral; no new budget bypass is introduced.
4. Successful version-2 historic collection writes version-2 marks. Identity shortfalls leave marks unset and retain durable resolver progress, so later ordinary eligible full runs continue. A full run may update the recovery-read timestamp even while identities remain unresolved; in an otherwise settled case the next progress opportunity is the next weekly full collection, rather than an immediate retry.

For regularly visited dossiers with sufficient allowance, first correction is expected by the first stale visit after the seven-day recovery interval (potentially another freshness window depending on visit cadence). Dormant dossiers have no wall-clock correction guarantee; the next ordinary eligible visit or a normal full manual refresh provides the opportunity. Do not promise immediate rollout recovery or silently introduce a global evidence-version bump.

Regression: start with a fresh completed run, a successful-but-empty version-1 settled tier mark and a recent recovery-read timestamp. Assert no reservation while fresh, a stale light run inside seven days, no timestamp extension from that light run, a stale full run after seven days, version-1 mark ignored, historic kill collected via resolved ID, and version-2 mark only after complete Raider.IO publication. Also cover a partial identity cap through successive ordinary eligible runs with persisted answers and zero Raider.IO-only scheduled retry.

## Approved concurrency safeguards implemented

Manager approval of c26f54fe additionally requires a persisted `retry_not_before`, atomic dispatch reservations and answers, and overlapping-subject regressions. The repository uses a five-minute per-locator lease and unique attempt token. A compare-and-set update saves proof only for that token; a stale response cannot replace a newer answer or release its lease. Every returned Retry-After extends the stored cooldown with a maximum, including late responses. A fresh saved answer remains reusable while the cooldown prevents additional physical reads. Attempt timestamps and cooldowns are checked before dispatch across ordinary and manual invocations.
