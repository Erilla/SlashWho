# Warcraft Logs ranked-kill backfill: provider contract and evidence boundary

Issue [#425](https://github.com/Erilla/SlashWho/issues/425). Reviewed 2026-09-23 after [PR #442](https://github.com/Erilla/SlashWho/pull/442) merged. This note separates the documented contract, the issue's earlier live observation, fresh public-client measurements, and staging results. All new probes used the `test` Railway worker's WCL credentials without printing or storing the secrets.

## Documented API contract

- The public v2 GraphQL client endpoint uses OAuth client credentials. Private reports require the user API and the report owner's authorization; `includePrivateLogs` on character rankings is available only through that user endpoint. [API documentation](https://www.warcraftlogs.com/api/docs), [Character](https://www.warcraftlogs.com/v2-api-docs/warcraft/character.doc.html).
- `Character.canonicalID` links an older character record after rename or transfer to its most recent version. `Character.hidden` indicates hidden rankings. `recentReports` is a paginated recent-report field, with a maximum `limit` of 100, and its schema does not promise complete historic coverage. [Character](https://www.warcraftlogs.com/v2-api-docs/warcraft/character.doc.html).
- `Character.zoneRankings` and `Character.encounterRankings` both return `JSON`, rather than a typed nested result. Each supports difficulty, metric, partition and timeframe. The schema documents `partition: -1` as all partitions, but the live result below selected one partition and omitted other public fight refs. `Historical` compares a ranking with results around its fight date. The schema warns rankings data may change without notice. The published schema defines neither the nested `ranks[].report` shape nor pagination/size limits for this character field. [Character](https://www.warcraftlogs.com/v2-api-docs/warcraft/character.doc.html), [RankingTimeframeType](https://www.warcraftlogs.com/v2-api-docs/warcraft/rankingtimeframetype.doc.html).
- A zone lists its supported partitions, and each partition has its own rankings, statistics and all stars. The special `-1` aggregate is therefore relevant to a historic tier with multiple partitions; whether every ranked kill appears in its aggregate response still requires measurement. [Zone](https://www.warcraftlogs.com/v2-api-docs/warcraft/zone.doc.html), [Partition](https://www.warcraftlogs.com/v2-api-docs/warcraft/partition.doc.html), [Character](https://www.warcraftlogs.com/v2-api-docs/warcraft/character.doc.html).
- `Report.rankedCharacters` lists characters ranked on kills in a report. Each ranked character's `server` is a `Server` object; it must be queried as `server { slug name }`. `Report.fights(fightIDs:)` identifies the exact fight; `ReportFight.kill`, `difficulty`, `encounterID`, `friendlyPlayers` and parallel `friendlySpecs` allow verification of the kill, boss, participation and spec. Actor IDs are local to the report, so `rankedCharacters.canonicalID` and a unique name/realm-to-actor link are needed for identity. [Report](https://www.warcraftlogs.com/v2-api-docs/warcraft/report.doc.html), [Character](https://www.warcraftlogs.com/v2-api-docs/warcraft/character.doc.html), [ReportFight](https://www.warcraftlogs.com/v2-api-docs/warcraft/reportfight.doc.html), [ReportActor](https://www.warcraftlogs.com/v2-api-docs/warcraft/reportactor.doc.html).
- `ReportData.report` can return null; the schema's `allowUnlisted` guidance describes the authorization risk when a multi-user app already knows an unlisted code. The public route cannot be treated as proof that private, unlisted, deleted or otherwise unavailable reports are retrievable. [ReportData](https://www.warcraftlogs.com/v2-api-docs/warcraft/reportdata.doc.html), [Report](https://www.warcraftlogs.com/v2-api-docs/warcraft/report.doc.html).
- `rateLimitData` exposes hourly limit, spent points and reset time. The schema publishes no fixed point price for a particular ranking query; costs must be measured by deltas with other traffic excluded. [RateLimitData](https://www.warcraftlogs.com/v2-api-docs/warcraft/ratelimitdata.doc.html).

## Earlier live observation, not repeated in this note

The updated [#425 issue body](https://github.com/Erilla/SlashWho/issues/425) records a credentialed public-client check on Ryun's canonical WCL character ID `40989140` in Antorus. `zoneRankings(zoneID: 17, difficulty: 5, partition: -1, timeframe: Historical)` reported 10 Garothi kills and one Argus kill. `encounterRankings` for Argus encounter 2092 returned report `y9DZNaRfzWQ46vj1`, fight 10 and spec Holy. The exact [public report](https://www.warcraftlogs.com/reports/y9DZNaRfzWQ46vj1#fight=10) confirmed a Mythic Argus kill, historical actor Erilla–Neptulon, and ranked-character canonical ID `40989140`. Garothi encounter 2076 returned 10 ranks for 10 `totalKills`, with nine Holy and one Discipline. These observations substantiate the direct path for two bosses of one character; they are not an all-tier completeness guarantee.

The same issue records approximately **11 WCL points** for 11 aliased encounter rankings, yielding **56 ranked kills in 39 distinct reports**; an exact report read cost approximately **2.2 points**. An earlier ten-report `recentReports` page cost approximately **20 points**. These are historical measurements reported by the issue, with no documented provider price guarantee. The fresh measurements below use separate, unaliased encounter queries and show 40 distinct Antorus report codes across both metrics. [#425](https://github.com/Erilla/SlashWho/issues/425), [rate-limit schema](https://www.warcraftlogs.com/v2-api-docs/warcraft/ratelimitdata.doc.html).

## Fresh public-client measurements, 2026-09-23

The probe used Ryun's stable WCL character ID `40989140`, Mythic difficulty 5, Historical timeframe and `partition: -1`. It read each tier's `dps` and `hps` zone rankings, then both metrics for every encounter with `totalKills > 0`. It counted exact `report.code`/`fightID` pairs in memory and printed aggregates only. All returned encounter rankings had the observed `ranks[].report` and `spec` shape; no sampled rank lacked a report reference. A zero below means this character had no ranked kill in that zone, not that the provider has no reports.

| Zone                  | Encounter-ranking calls | Zone `totalKills` sum | Unique exact fights across metrics | Distinct report codes | Overlap of metric refs | Measured ranking points¹ |
| --------------------- | ----------------------: | --------------------: | ---------------------------------: | --------------------: | ---------------------: | -----------------------: |
| Antorus (17)          |                      22 |                    56 |                                 60 |                    40 |    52 of 56 per metric |       32.23 for 23 calls |
| Tomb of Sargeras (13) |                      16 |                    40 |                                 40 |                    25 |               40 of 40 |       26.17 for 17 calls |
| Uldir (19)            |                      14 |                    28 |                                 28 |                    23 |               28 of 28 |       24.15 for 15 calls |
| Castle Nathria (26)   |                       0 |                     0 |                                  0 |                     0 |                      — |  10.01 for one zone call |

¹ The API's `rateLimitData.pointsSpentThisHour` counter was read immediately before and after each tier, during a quiet interval after the staging run ended. The meter read itself cost 1 point; the reported amounts subtract the final meter read. A two-metric zone ranking cost 10.01 points, and individual encounter-ranking calls cost 1.01 points. These are observed prices on this key and date, not a provider promise. The 60 Antorus pairs exceed the zone's 56 `totalKills`, and four fights were exclusive to each metric: neither one-metric collection nor `totalKills` is a completeness test. No tier-wide report hydration was attempted, so these are ranking costs, not complete backfill costs. [Rate-limit schema](https://www.warcraftlogs.com/v2-api-docs/warcraft/ratelimitdata.doc.html), [Character rankings schema](https://www.warcraftlogs.com/v2-api-docs/warcraft/character.doc.html).

**Partition counterexample.** Antorus Garothi (`encounterID: 2076`) returned 10 healing fight refs with `partition: -1` and reported selected partition 1. Explicit partition 2 returned two different refs; partition 3 returned one more. Tomb's `encounterID: 2032` returned six refs under `-1`, matching explicit partition 2, while explicit partition 1 returned eight different refs. `partition: 0` on Garothi also selected partition 1. Thus, for these observed responses, `-1` did not aggregate every partition despite the documented intent. The corrected route must enumerate `Zone.partitions` explicitly. [Zone and partitions schema](https://www.warcraftlogs.com/v2-api-docs/warcraft/zone.doc.html), [Character rankings schema](https://www.warcraftlogs.com/v2-api-docs/warcraft/character.doc.html).

**Exact Argus hydration.** A public-client query for report `y9DZNaRfzWQ46vj1`, fight 10 returned zone 17, encounter 2092, Mythic difficulty, `kill: true`, actor `Erilla–Neptulon` in `friendlyPlayers`, and one `rankedCharacters` record with `canonicalID: 40989140` and `server: { slug: "neptulon", name: "Neptulon" }`. The query used by PR #442 (`rankedCharacters { ... server }`) instead returned HTTP 200 with a GraphQL validation error: `Field "server" of type "Server!" must have a sub selection.` After correcting the query and actor match in local source, `getRankedKillReports` with a cursor limited to Argus returned the exact [public fight](https://www.warcraftlogs.com/reports/y9DZNaRfzWQ46vj1#fight=10), killed 2018-06-20, in three WCL requests. This proves the current source gateway's attribution on that known fight, not staging publication or whole-tier coverage.

**Hydration in three tiers.** With a cursor limited to one encounter and one explicit partition, the corrected source gateway accepted both Antorus Garothi partition 2 refs (two hydration requests) and six Uldir `encounterID: 2144` refs (six hydration requests). Tomb `encounterID: 2032` partition 1 produced eight exact public Mythic kill reports, but each report returned `rankedCharacters: null`. The gateway cannot safely attribute those eight fights to Ryun and accepted zero; it now skips each once and continues instead of stopping at the first as `schema_drift`. Its two metric rankings otherwise caused 16 reads of those eight reports before that deduplication fix. This is a measured coverage limit: a ranking reference and a public kill do not guarantee report-level canonical identity.

The cursor carries only accepted public fight keys to avoid rehydrating those fights after a capped run resumes. It does not persist the codes of unattributed, private or missing reports. Those may cost another read in a later run, while the in-call deduplication still avoids reading the same null `rankedCharacters` response twice in one run.

## Staging acceptance result and remaining limits

The `test` web and worker had successfully deployed PR #442 at commit `6e776aed` when the Ryun/Silvermoon Antorus tier search was queued. Its run completed `partial` with `unavailable`, at the first ranked report hydration, and published no Antorus boss evidence in the dossier. Its persisted cursor reached zone 17 and the first of 11 encounters. The whole tier-search run spent **1,484.6 WCL points**, including 23 ordinary history requests, 38 tier-search requests, three ranking requests and one limited report hydration; the full-run point figure cannot be assigned to ranked discovery alone. This is a failed staging acceptance for the deployed PR #442, explained by the invalid ranked-character `server` selection above. The source fix awaits deployment; a new staging run must verify publication and continuation. [PR #442](https://github.com/Erilla/SlashWho/pull/442), [`client.ts`](../../packages/warcraftlogs/src/client.ts).

Private, unlisted, deleted and inaccessible reports remain outside the public-client guarantee. Hidden rankings, ambiguous actor matches, transfers beyond the known Erilla/Ryun example, and much larger ranking payloads were not sampled live. The code skips absent or ambiguous evidence and fixtures cover wrong canonical ID and conflicting spec, but fixtures do not establish the frequency of these provider cases. Wipe-only and unranked kills cannot come from this ranking route; guild attendance and explicit tier search remain separate recovery paths. The API does not document a nested rank pagination or size limit, so broad coverage cannot be inferred from the sampled tiers. [Character](https://www.warcraftlogs.com/v2-api-docs/warcraft/character.doc.html), [ReportData](https://www.warcraftlogs.com/v2-api-docs/warcraft/reportdata.doc.html), [Report](https://www.warcraftlogs.com/v2-api-docs/warcraft/report.doc.html).
